# 동기화 기법 & 교착 상태

## 12-2 동기화 기법

프로세스·스레드 동기화를 위한 대표적인 세 가지 도구인 **뮤텍스 락, 세마포어, 모니터**를 살펴본다. 각 도구가 어떻게 상호 배제와 실행 순서 제어를 이루는지에 주목한다.

### 뮤텍스 락 (Mutex Lock)

**상호 배제**를 위한 동기화 도구로, 탈의실의 **자물쇠**와 같은 역할을 한다. (손님 = 프로세스, 탈의실 = 임계 구역) 전역 변수 하나와 함수 두 개로 간단히 구현할 수 있다.

| 구성 요소 | 역할 |
| --- | --- |
| **lock** (전역 변수) | 자물쇠 역할. `true`면 임계 구역이 잠김(사용 중), `false`면 열림 |
| **acquire()** (함수) | 임계 구역 진입 **전** 호출. 잠겨 있으면 열릴 때까지 반복 확인하고, 열려 있으면 잠그고 진입 |
| **release()** (함수) | 임계 구역 작업 **후** 호출. lock을 `false`로 바꿔 자물쇠를 풂 |

```
acquire() {
    while (lock == true)   // 잠겨 있으면 반복 확인 (대기)
        ;
    lock = true;           // 잠그고
    // 임계 구역 진입
}

release() {
    lock = false;          // 자물쇠 해제
}
```

> **바쁜 대기(busy waiting)** — acquire의 `while` 문처럼, 임계 구역이 열렸는지 무한히 반복하며 확인하는 방식. (탈의실 문을 쉴 새 없이 덜컹거리는 것과 같아) CPU 사이클을 낭비하므로 좋은 방식은 아니다.

### 세마포어 (Semaphore)

뮤텍스 락과 비슷하지만, **공유 자원이 여러 개** 있는 경우에도 적용할 수 있는 더 일반화된 도구다. (자물쇠 하나만 상정한 뮤텍스 락과 달리) 이름은 **철도 신호기**에서 유래했다 — 신호기가 내려가 있으면 대기, 올라가 있으면 진입.

> 세마포어에는 이진 세마포어와 카운팅 세마포어가 있는데, 뮤텍스와 유사한 이진 세마포어보다 더 일반화된 **카운팅 세마포어**를 세마포어로 지칭한다.

| 구성 요소 | 역할 |
| --- | --- |
| **S** (전역 변수) | 임계 구역에 진입 가능한 프로세스 개수(= 사용 가능한 공유 자원 개수) |
| **wait()** (함수) | 임계 구역 진입 **전** 호출. 진입해도 되는지/기다려야 하는지 판단 |
| **signal()** (함수) | 임계 구역 작업 **후** 호출. 기다리는 프로세스에 "통과" 신호 |

```
wait() {
    S--;
    if (S < 0)             // 사용 가능한 자원이 없으면
        // 대기 큐에 삽입하고 대기 상태로 (sleep)
}

signal() {
    S++;
    if (대기 중인 프로세스 존재)
        // 대기 큐에서 꺼내 준비 상태로 (wakeup)
}
```

> **바쁜 대기 해결** — 단순 구현은 `S <= 0`일 때 무한 반복(바쁜 대기)한다. 이를 개선해, 사용할 자원이 없으면 프로세스를 **대기 상태**로 만들어 대기 큐에 넣고(CPU 사이클 절약), 자원이 생기면 **준비 상태**로 되돌린다.

> **실행 순서 제어** — 세마포어는 실행 순서 제어에도 쓸 수 있다. P1이 P2보다 먼저 실행되어야 한다면, **S를 0으로 두고** P1 뒤에 `signal()`, P2 앞에 `wait()`를 붙인다. 그러면 P2가 먼저 실행돼도 wait에 막혀, 반드시 P1 → P2 순서가 보장된다.

### 모니터 (Monitor)

세마포어는 임계 구역 앞뒤로 wait·signal을 매번 명시적으로 호출해야 해서 실수(누락·중복·순서 착오)가 잦고 디버깅이 어렵다. **모니터**는 개발자가 다루기 편리한 동기화 도구로, **상호 배제와 실행 순서 제어를 모두** 제공한다. (대표적으로 자바가 활용)

**상호 배제** — 모니터는 **공유 자원과 그 접근 통로(인터페이스)를 묶어** 관리하고, 접근하려는 프로세스는 반드시 인터페이스를 통해서만 접근하게 한다. 인터페이스를 위한 큐에 줄을 세워, **한 번에 하나의 프로세스만** 모니터에 진입해 공유 자원을 다루도록 한다.

**실행 순서 제어** — 내부적으로 **조건 변수(condition variable)**를 사용한다. 조건 변수는 `wait()`·`signal()`로 호출하는 특별한 변수로, 조건 변수마다 별도의 큐가 있다.

| 연산 | 동작 |
| --- | --- |
| **wait()** | 조건 변수에 대한 큐에 삽입하고 프로세스를 **대기 상태**로 변경 |
| **signal()** | wait로 대기 중이던 프로세스를 **다시 실행(준비 상태)**할 수 있게 변경 |

> 상호 배제를 위한 큐(모니터 진입 큐)와 실행 순서 제어를 위한 큐(조건 변수 큐)는 서로 다르다. 특정 프로세스가 실행될 조건이 안 됐을 때는 `wait()`로 실행을 중단하고, 조건이 충족되면 다른 프로세스가 `signal()`을 호출해 실행을 재개시키는 방식으로 순서를 제어한다.

## Chapter 13. 교착 상태

## 13-1 교착 상태란

두 개 이상의 프로세스가 각자 자원을 점유한 채 서로가 가진 자원을 기다리기만 하면, 어떤 프로세스도 실행되지 못하고 멈춰버린다. 이를 **교착 상태(deadlock)**라 한다. 교착 상태를 해결하는 것도 운영체제의 중요한 업무다.

### 식사하는 철학자 문제

교착 상태를 설명하는 고전적 문제(Dining Philosophers Problem)다.

- 둥근 식탁에 철학자 5명이 앉아 있고, 철학자 사이사이에 포크가 있다. 식사하려면 **양쪽 포크 2개**가 모두 필요하다.
- 각 철학자는 "생각 → 왼쪽 포크 집기 → 오른쪽 포크 집기 → 식사 → 오른쪽 내려놓기 → 왼쪽 내려놓기 → 반복" 순으로 행동한다.
- **모든 철학자가 동시에** 왼쪽 포크를 집으면, 모두가 오른쪽 포크를 기다리게 되어 아무도 식사하지 못하고 영원히 기다린다.

> **대응 관계** — 철학자 = 프로세스·스레드, 포크 = 자원, 식사 = 자원을 이용한 실행. 서로가 점거한 자원을 서로 기다리면 어떤 프로세스도 끝까지 실행될 수 없음을 보여준다.

### 자원 할당 그래프

교착 상태 발생 상황을 표현하는 그래프다. 그리는 방법은 다음과 같다.

- **프로세스**는 원, **자원의 종류**는 사각형으로 표현한다.
- 사용 가능한 자원의 개수는 사각형 안에 **점**으로 표현한다. (자원이 3개면 점 3개)
- 프로세스가 자원을 **할당받았으면** 자원 → 프로세스로 화살표를 그린다.
- 프로세스가 자원을 **기다리고 있으면** 프로세스 → 자원으로 화살표를 그린다.

> **교착 상태의 특징** — 교착 상태가 일어난 자원 할당 그래프는 **원(cycle)의 형태**를 띤다. (단, 원 형태라고 반드시 교착 상태인 것은 아니다. 하지만 교착 상태라면 반드시 원 형태를 띤다.)

### 교착 상태 발생 조건

교착 상태는 다음 **네 가지 조건을 모두** 만족할 때 발생할 수 있다. 하나라도 만족하지 않으면 발생하지 않는다.

| 조건 | 의미 |
| --- | --- |
| **상호 배제(mutual exclusion)** | 한 프로세스가 사용하는 자원을 다른 프로세스가 사용할 수 없음 |
| **점유와 대기(hold and wait)** | 자원을 할당받은 상태에서 다른 자원을 기다림 |
| **비선점(non-preemption)** | 어떤 프로세스도 다른 프로세스의 자원을 강제로 뺏지 못함 |
| **원형 대기(circular wait)** | 프로세스들이 원의 형태로 자원을 대기함 (자원 할당 그래프가 원 형태) |

> 식사하는 철학자 문제로 보면: 포크는 한 명만 쓸 수 있고(상호 배제), 왼쪽 포크를 든 채 오른쪽을 기다리며(점유와 대기), 남의 포크를 뺏지 못하고(비선점), 모두가 원형으로 서로를 기다린다(원형 대기).
